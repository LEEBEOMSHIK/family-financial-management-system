# 에이전트 팀 구성과 인수인계

역할은 책임의 분리이며 제품 사용자 역할(RBAC)과 다르다. `.agents/roles/*.md`는 도구에 종속되지 않는 작업 프롬프트다. 설치된 에이전트, 자동 실행 권한, 모델/플러그인 설정을 생성한 것은 아니다. 현재 사용하는 도구가 지원하는 방식으로 필요한 역할 문서만 읽혀 실행한다.

## 책임표

| 역할 | 책임·주요 산출물 | 입력 / 인수 대상 | 독단 결정 금지 |
| --- | --- | --- | --- |
| 조정·기획 product | 요구사항·규정 매핑·범위·우선순위·AC | 원문/요청 → 모든 역할 | 회비/승인/투표 규정 창작 |
| 아키텍처 architecture | 경계·API/이벤트 계약·ADR·의존성 | 요구사항 → FE/BE/DB/AI/운영 | 사용자 확정 제약 변경 |
| 프론트 frontend | 화면·상태·타입·접근성 구현 | 계약/디자인 → QA | UI 가드만으로 권한 처리 |
| 백엔드 backend | 업무 서비스·인가·트랜잭션·어댑터 | 정책/API/DB → QA/통합 | 자동 송금·무검증 외부 호출 |
| 데이터 database | 모델·제약·인덱스·이관·대사 | 업무 불변식 → BE/QA/운영 | 확정 원장 파괴·개인정보 샘플 |
| AI ai | 허용 조회·ACL 검색·근거·평가 | 권한/문서 모델 → QA/보안 | 임의 SQL·무허가 자료 전송 |
| QA qa | 위험 기반 시나리오·회귀·증거·재현 | 요구사항/구현 → 조정/리뷰 | 미실행 검증 통과 표시 |
| 보안 security | 위협 모델·권한·증빙·세션·공급망 | 설계/변경 → 전체 | 업무규정 승인 대행 |
| 디자인 design | 토큰·컴포넌트·패턴·문구·a11y | 사용자/업무 흐름 → FE/QA | 금융 상태를 색상만으로 표현 |
| 운영 operations | 로컬 실행·CI·운영 Docker·복구·모니터링 | 잠금 파일/운영 요구 → QA/책임자 | 요청 없는 운영 배포/발송 |
| 독립 리뷰 review | 요구사항/설계/구현/검증 일치 확인 | 변경 diff와 증거 → 조정 | 자기 구현을 독립 검수로 표시 |

사람인 프로젝트 책임자는 업무 정책과 운영 활성화의 최종 결정자다. 조정 에이전트는 결정되지 않은 문제를 드러내고, 관련 없는 작업을 계속하도록 범위를 나눈다.

## 작업 배분 규칙

작업 하나에 하나의 주 담당(owner)을 둔다. 시작 전에 요구사항 ID, 수정 가능 파일, 수정 금지 파일, 사용하는 계약 버전, 테스트, 인수자를 기록한다. 여러 에이전트는 같은 파일을 동시에 편집하지 않는다. API/DB 계약의 변경은 architecture와 database 담당이 먼저 합의하고 소비자에게 전파한다. 불변식에 영향을 주는 변경은 backend+security+QA 검토를 받는다.

병렬화 가능한 예: 확정된 계약 위의 화면 스타일/합성 fixture 작성. 순차 작업 예: 규정 매핑 → 승인 상태 설계 → DB/API → FE 연결 → E2E. 공유 브랜치 작업이라면 파일 소유권을 명시한다. 격리가 필요한 경우 기존 적합한 체크아웃/작업 공간을 먼저 확인한다.

## 인수인계 계약

모든 인수인계는 `docs/templates/handoff.md`를 채운다.

- Input: 문제, 근거 문서 버전, 요구사항, 확정/미확정 항목, 수정 범위.
- Output: 변경 파일과 commit/diff(있는 경우), API/이벤트/타입 변화, 마이그레이션, 사용자 동작.
- Evidence: 실제 실행 명령/환경/결과, 스크린샷 또는 테스트 이름, 미실행 항목과 이유.
- Risk: 데이터/권한/금액/알림 영향, 남은 결함, 되돌리는 방법.
- Next: 인수자, 다음 행동, 재현용 합성 데이터, 차단 조건.

인수자는 계약 버전과 필수 테스트를 확인하여 `accepted`, `changes_requested`, `blocked_by_decision` 중 하나로 답한다. ‘작성함’은 인수 완료가 아니다. 반려 시 관찰된 문제·위험·수용 기준을 구체적으로 남기며 개선 방법 하나를 무조건 강요하지 않는다.

## 충돌과 결정

업무 해석은 product가 규정 소유자에게, 기술 경계는 architecture가 ADR로, 보안 위험은 security가 근거와 완화안을 제시한다. 역할끼리 의견이 다르다고 정책을 임의로 확정하지 않는다. 해결 안 된 항목은 issue의 decision-needed에 연결하고 영향 기능만 비활성으로 유지한다.

## 기본 실행 요청 형식

‘AGENTS.md와 .agents/roles/backend.md를 읽고 TASK-03을 수행하라. 범위는 apps/api의 expense 모듈이다. 입력은 R04/R13, ADR-0001, API 계약 v0.1이다. U06 미확정 경로는 거부하고 합성 정책으로 테스트하라. 완료 시 handoff 템플릿에 실제 검증 결과를 남겨라.’

이 문장은 실행 예시이며 현재 어떤 도구에 작업을 예약·발송하는 설정이 아니다.

## 지침 파일 크기 관리

역할 문서를 생성·수정·인수할 때 [공통 지침의 크기·참조 규칙](../../AGENTS.md)을 적용한다. 각 파일은 빈 줄을 포함하여 200줄 이하여야 한다. 초과할 상세 절차나 예시는 `.agents/references/` 등에 주제별로 분리하고, 원본 역할 문서에 상대 경로·목적·읽는 조건을 남긴다. 참조 파일도 같은 제한을 적용하며 공통 불변식을 복사하거나 약화하지 않는다. 현재 역할 프롬프트 11개는 각각 18줄로 분리할 필요가 없다.
