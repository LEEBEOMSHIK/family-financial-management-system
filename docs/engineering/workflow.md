# 표준 개발 절차와 Definition of Done

## 상태 흐름

`intake → ready → designing → ready_to_build → implementing → verifying → reviewing → documenting → done`

`blocked_by_decision`은 어느 단계에서도 특정 이슈에 적용할 수 있다. 영향을 받지 않는 작업까지 멈추지 않는다. 디자인/문서 전용 요청은 구현 단계를 ‘해당 없음’으로 명시할 수 있다.

| 단계 | 책임 / 입력 | 필수 산출물 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 요구사항 | product / 요청·규정 | R-ID, 사용자, 범위, Given/When/Then, 결정 상태 | 업무 근거 또는 명시적 차단 경로 |
| 설계 | architecture+design+DB / 요구사항 | 상태·권한·데이터·API·화면, ADR 필요 판단 | 계약과 예외/동시성/복구가 설명됨 |
| 구현 | FE/BE/DB/AI / 설계 | 작은 diff, 마이그레이션, 필요한 테스트 | 불변식 유지, 타입/정적 검사 |
| 테스트 | QA / AC와 변경 | 실행 결과, 권한/금액/날짜/재시도, 화면 증거 | 필수 시나리오 통과 또는 기능 비활성 |
| 리뷰 | 독립 reviewer+security / diff·증거 | 위험 우선 피드백, 해결 기록 | 차단 결함 없음, 계약/규정 정합 |
| 문서화 | 구현 담당+product / 최종 동작 | 사용자 흐름, 운영/복구, ADR·목차·handoff | 실제 결과와 문서 일치 |
| 종료 | 조정 담당 / 인수 결과 | DoD, 남은 이슈, 릴리스 판단 | 작업 범위의 DoD 만족 |

## Definition of Ready

- [ ] 대상 사용자·문제·R-ID가 있다.
- [ ] 성공/실패/권한/빈 값의 인수 기준을 정의했다.
- [ ] 필요한 업무 규정 버전이 있거나 미설정 시 차단 동작이 명확하다.
- [ ] API/DB/화면 계약, 파일 범위, 담당/인수자를 정했다.
- [ ] 외부 API가 없어도 테스트할 fixture/adapter 경계를 정했다.
- [ ] 파괴적 변경·운영 발송·비용 발생의 권한 범위를 확인했다.

## Definition of Done — 제품 변경

- [ ] 요구사항의 모든 AC와 권한 거부 사례가 통과했다.
- [ ] 중복 제출·동시 갱신·금액/날짜 경계·외부 타임아웃을 다뤘다.
- [ ] 감사 이벤트·증빙 이력·policy_version·request_id가 추적 가능하다.
- [ ] DB 제약·마이그레이션·복구 방식이 검증됐다(해당 시).
- [ ] 타입·lint·단위/통합/E2E 중 필요한 검사를 실제 실행했다. 명령/환경/결과를 기록했다.
- [ ] loading/empty/error/forbidden/stale/success 상태와 키보드/모바일을 확인했다.
- [ ] 개인정보/비밀/권한 없는 데이터가 로그·캐시·파일·AI로 새지 않는다.
- [ ] 공식 API/라이브러리 선택의 검증 근거·정확한 버전·잠금 파일이 있다.
- [ ] 독립 리뷰의 차단 결함을 해결하고 문서·ADR·계약을 갱신했다.
- [ ] 인수자가 결과를 재현할 수 있다. 미검증 조건을 완료라고 쓰지 않았다.

## Definition of Done — 이번 개발 기반 문서 묶음

- [ ] 사용자 확정 조건이 요구사항·AGENTS·설계·설정 사이에 일치한다.
- [ ] 운영규정 원문과 API 자격의 미확정을 명시했다.
- [ ] 모든 요청 항목에 파일이 있고 상대 링크가 존재한다.
- [ ] JSON/TOML/CSS 토큰 및 예제의 구조를 검증했다.
- [ ] 디자인 미리보기의 데스크톱/모바일 구성을 확인하고 제한을 기록했다.
- [ ] 검증 보고서는 제품 구현 테스트와 구별된다.

## ADR을 작성하는 경우

새 프레임워크/인증/DB/AI 공급자, 공개 API 변경, 원장 불변식, 권한 모델, 알림/대사 의미, 운영 복구 목표, 파괴적 이관이면 ADR을 작성한다. 단순 문구/스타일 버그 수정은 ADR 없이 이슈로 설명 가능하다.

ADR 상태는 proposed→accepted→superseded/rejected. accepted 전에는 누가 언제 승인했는지 기록한다. 이 묶음에서 사용자 확정 사항을 옮긴 ADR은 accepted-from-request로 표시하며, 세부 설계까지 승인된 것으로 확대하지 않는다.

## 결함 분류

P0: 금액 손상·권한 누출·오송금 실행·증빙 소실. 즉시 영향 기능 중지/복구 검토.
P1: 승인 우회·중복 원장·잘못된 총무 발송·투표 결과 오류. 출시 차단.
P2: 주요 흐름의 접근성/사용성·대사 안내 오류. 해당 범위 출시 전 수정.
P3: 사소한 문구/시각 문제. 범위·일정을 기록해 추적.

현재 초안에 있는 미확정 자체는 제품 버그가 아니다. 미확정 값을 정상 정책처럼 활성화하는 것이 결함이다.
