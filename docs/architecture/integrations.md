# 은행·엑셀·일정·알림 연동

## 1. 확인한 사실과 미검증 조건

확인일: 2026-10-23. 공개 문서 확인은 실제 계정의 계약/심사/운영 가능 확인과 다르다.

| 영역 | 공식 문서로 확인한 사실 | 이 프로젝트의 미검증 사항 |
| --- | --- | --- |
| 오픈뱅킹 | 잔액·거래 조회 API가 있으며 이용기관은 계약과 이용승인을 받는 구조 | 가족 모임 운영 주체가 이용기관/제휴 고객이 될 수 있는지, 카카오뱅크 해당 계좌/명의/동의 지원 |
| 카카오 메시지 API | 같은 서비스 사용자 간 메시지이며 친구 기능에 권한·동의 조건 존재 | 무인 예약 알림 목적 적합성, 수신 연결·토큰 유지·심사 |
| 알림톡 | 정보성 메시지, 승인 템플릿, 비즈니스 채널 설정 및 공식 딜러 경로 | 가족 모임의 가입 자격, 해당 문안 승인, 비용, 제공자 장애·결과 조회 |

근거: [금융결제원](https://openapi.kftc.or.kr/service/openBanking), [카카오 메시지](https://developers.kakao.com/docs/ko/kakaotalk-message/common), [알림톡](https://kakaobusiness.gitbook.io/main/ad/infotalk).

**추론/설계 제안:** 자동 업무 리마인더에는 알림톡을 먼저 조사한다. 친구 API나 ‘나에게 보내기’를 일반 가족 알림의 대체 수단으로 확정하지 않는다. 카카오뱅크가 오픈뱅킹에 참여한다는 사실만으로 이 앱에 직접 API 권한이 있다고 결론 내리지 않는다.

## 2. 은행 포트

`BankReadPort`의 계약은 `capabilities()`, `get_balance(account_ref)`, `list_transactions(account_ref, start, end, cursor)`로 한정한다. `BalanceSnapshot`은 amount_krw, currency, as_of, source, completeness를 반환한다. `TransactionPage`는 정규 거래 목록, next_cursor, coverage와 fetched_at을 반환한다. 지원하지 않는 기능은 `CAPABILITY_UNAVAILABLE`로 명시하며 숫자 0이나 빈 정상 결과로 위장하지 않는다.

은행 인증은 서버 어댑터 내부다. 브라우저에 금융 API token을 노출하지 않는다. 거래 조회는 페이지 끝까지 수집했는지 기록하고 호출 제한·만료·중간 실패·기간 겹침을 처리한다. 모든 데이터는 staging을 거친다. 계좌 명의나 모임통장 ‘보기’ 권한이 API 조회 권한과 동일하다고 가정하지 않는다.

`StatementImportPort.parse(file_ref, mapping_version)`는 파일 파싱/정규화를 담당한다. 파일 어댑터를 실시간 은행 API인 것처럼 구현하지 않는다. 새 은행은 같은 정규 모델, 중복 후보 검사, 권한/감사 계약 테스트를 통과해야 한다.

## 3. 거래 파일 가져오기/내보내기

권장 초기 형식은 `.xlsx`와 UTF-8 CSV이며 `.xls`, `.xlsm`, 암호화 파일은 기본 거부 제안이다. 실제 카카오뱅크 서식과 호환 여부를 확인한 뒤 허용 형식/변환 절차를 결정한다. 외부 링크·수식·매크로를 실행하지 않는다. 거래 파일 한도 제안: 10 MiB, 50,000행, 압축 해제 100 MiB, 처리 제한 60초. 초과는 분할 안내한다.

흐름: 업로드 권한 → 파일 해시/형식/압축 크기 검사 → 비공개 격리 → 매핑 선택 → 날짜/금액/계좌/통화 검사 → 오류행·중복 후보·총합 미리보기 → 총무 확정 → 한 트랜잭션 원장 반영 → 결과/감사 기록. 재업로드·재확정은 기존 결과를 반환한다.

정규 컬럼:

| 키 | 규격 | 필수 여부 |
| --- | --- | --- |
| account_ref | 서버에 등록된 내부 계좌 ID | 필수 |
| occurred_at | ISO-8601 offset 시각; 출처가 날짜만 주면 정밀도 별도 기록 | 필수 |
| direction | CREDIT 또는 DEBIT | 필수 |
| amount_krw | 양수 정수 문자열 | 필수 |
| description | 길이 제한 있는 텍스트 | 선택 |
| provider_tx_id | 은행 고유 식별자 | 있으면 보존 |
| balance_after_krw | 정수 문자열; 의미·시점 검증 필요 | 선택 |
| source_row | 원본 행/시트 위치 | 필수 |

데이터 오류가 있으면 전체 확정을 막고 오류 보고서를 제공하는 방식을 초기 제안으로 둔다. 부분 확정이 필요하면 명시적 제외 행과 제외 사유를 저장하는 별도 설계를 채택한다. 합법적인 동일 시각/동일 금액 거래는 자동 삭제하지 않는다.

내보내기는 필터·기간·마스킹 범위·요청자를 고정한 job이다. 생성 시점과 다운로드 시점 모두 권한을 확인한다. 파일에는 조회 기준일/정책 버전/통화/합계를 포함하고 원본 계좌번호·비공개 증빙 URL을 넣지 않는다. 문자열은 XLSX의 텍스트 타입으로 기록하고, CSV의 수식 실행 가능 선두 문자와 제어 문자는 안전하게 처리한다. 실제 금액 열은 검증한 정수 데이터만 사용한다. 링크는 인증이 필요한 앱 상세 페이지로 제공한다.

## 4. 일정 모델과 알림 확정 조건

행사 날짜와 송금 날짜를 각각 둔다. 반복 일정은 연도별 occurrence로 전개한다. 음력 변환·공휴일 이동은 라이브러리/정책 미검증이며 자동 적용하지 않는다. occurrence마다 취소·날짜 변경·예산 변경을 기록한다. 지출 예정만 있고 승인이 없으면 ‘승인 필요’ 목록에 두고 송금 지시 문구를 보내지 않는다.

사용자 확정: D-1, D0, 미처리 D+1 / 현직 총무 / 카카오톡 우선.
초안 제안: KST 09:00, 해당 날짜 안에서만 누락분 보충, 휴일 자동 이월 없음, scheduled 상태만 대상. 운영 전 U08 확인 필요.

| 날짜 | 대상 조건(제안) | 문안 예시(템플릿 미승인) |
| --- | --- | --- |
| D-1 | 승인된 지급, 아직 송금 기록 없음 | 내일 송금 예정 건이 있습니다. 로그인 후 내용을 확인해 주세요. |
| D0 | 동일 조건 | 오늘 송금 예정 건이 있습니다. 은행 앱에서 처리한 뒤 송금 내역을 기록해 주세요. |
| D+1 | 동일 조건이 계속 유지 | 어제 송금 예정 건의 처리 기록이 없습니다. 실제 송금 여부를 확인해 주세요. |

실제 메시지는 민감한 사유·수취 계좌·영수증·잔액을 넣지 않는다. 링크는 허용된 서비스 도메인의 인증 필요 경로다. D+2 이후 반복 독촉은 범위 밖이다. 이미 reported_paid/reconciled/cancelled이면 미발송 이벤트를 취소한다.

## 5. worker 및 중복 통제

1. UTC `now`를 KST 업무일로 변환한다. 각 지급의 `due_date + offset` 날짜에 scheduled event를 생성한다.
2. unique `(family_id, intent_id, schedule_revision, offset_day)`로 논리 이벤트를 하나만 만든다. channel과 수신자는 delivery_attempt에 둔다.
3. DB lease/lock으로 한 worker만 claim한다. 발송 직전에 최신 지급 상태·유효 approval_revision·일정 버전·현직 총무·수신 연결/동의를 재검사한다. 승인 개정으로 superseded된 intent는 발송하지 않는다.
4. 현직 총무 0명/복수 또는 연결 불가면 `blocked_recipient`로 두고 웹 운영 예외 목록에 남긴다. 전임자나 임의 가족에게 발송하지 않는다.
5. `(family_id, obligation_id, local_date, offset_day, channel)` 고유 delivery_slot을 잠가 개정 간 발송을 직렬화한다. 제공자 idempotency key가 있으면 안정적인 slot ID를 사용한다. 제공자의 접수 상태와 배달 상태를 분리해 저장한다.
6. 확실한 일시 오류만 지수 backoff(예: 1·5·30분)로 제한 재시도한다. 최종 실패는 `failed`, 결과 불명 타임아웃은 `unknown`으로 두고 제공자 조회/운영 확인 전 맹목적 재발송을 금지한다.
7. 성공은 provider message ID와 시간으로 기록한다. webhook은 서명·replay·이벤트 ID를 검증한다. 제공자가 배달 결과를 주지 않으면 ‘발송 요청 접수’까지만 표시한다.

외부 시스템까지 exactly-once를 보장한다고 주장하지 않는다. 내부 중복 방지와 제공자의 기능에 따른 best-effort 처리다. 지급/일정 수정과 외부 발송 사이의 짧은 경쟁 상태는 메시지에 최소 정보만 넣고 접속 후 최신 상태를 보여 주는 방식으로 제한한다.

당일 생성이 09:00 이후라면 당일 유효 알림만 생성한다. 늦은 복구 시 이전 날짜 알림을 모두 몰아 보내지 않는다. D+2에 복구하면 송금 알림은 보내지 않고 누락을 운영 예외로 남긴다. D+1에 복구하면 그날의 미처리 알림 하나만 보낸다. 일정 변경은 revision을 증가시키고 이전 미발송 이벤트를 취소한다. 같은 날짜·offset에 이미 전달한 알림이 있다면 자동 반복하지 않고 변경 사실을 웹에 표시한다.

개정 간 발송 보류: 같은 slot에 accepted/delivered/unknown 시도가 있으면 새 schedule_revision, 새 intent 또는 새 총무로도 자동 발송하지 않는다. unknown은 제공자 상태 조회나 운영 확인으로 결과가 확정될 때까지 보류한다. 명시적으로 미접수/최종 미배달이 확인된 경우에만 같은 날의 유효 조건과 현직자를 재검사하여 재시도한다. 제공자 key 재사용 규칙을 계약 테스트로 검증하고 필요할 때만 확인된 실패 이후 attempt 번호를 추가한다. 불명확한 상태에서 새로운 키를 만들어 재발송하지 않는다. 이미 접수/전달된 메시지는 회수된 것으로 표시하지 않는다.

## 6. 비활성 기본값과 대안

개발은 `NOTIFICATION_TRANSPORT=sink`, 외부 발송 false다. 알림 정책 JSON의 offset enabled는 정책의 활성 의미이며 실제 공급자 발송 허용을 뜻하지 않는다. 카카오 사용 조건이 충족되지 않으면 웹 알림함과 총무의 수동 확인을 대안으로 제안하되 카카오 요구 완료로 보고하지 않는다. SMS/이메일 추가 발송은 별도 채택 결정과 수신/비용 정책이 필요하다.
