# 로컬 개발과 운영 배포의 분리

상태: 운영 설계 초안. WB-09의 [EC2 운영 인증·복구 준비](ec2-readiness.md)를 진행한다. 배포 파일·클라우드 계정·도메인·예약 작업은 아직 생성하지 않았다.

## 운영 구성 제안

Docker는 운영에서 Next.js, FastAPI, worker를 각각 격리하는 데 사용한다. TLS reverse proxy 뒤에 웹과 API를 동일 출처로 제공한다. PostgreSQL과 객체 저장소는 관리형 우선 검토이며 자체 운영 시 패치·백업 책임을 지정한다. API와 worker는 동일 버전의 도메인 코드를 사용한다. worker를 API 컨테이너의 메모리 타이머로 실행하지 않는다.

운영 이미지에는 고정 버전/잠금 파일, non-root user, 최소 파일 권한, 읽기 전용 루트(필요한 임시 경로 제외), health/readiness 검사를 적용한다. 비밀은 이미지/compose 파일에 넣지 않고 런타임 비밀 저장소에서 주입한다. DB 포트를 인터넷에 공개하지 않는다. 외부 카카오/은행/LLM 키는 기능별로 분리한다.

## 배포 순서

1. 채택 ADR·규정 매핑·실계정 연결 조건·담당자·백업/복구 증거를 확인한다.
2. CI에서 잠금 파일 기반 build/type/lint/unit/integration/E2E와 취약점/비밀 검사를 수행한다.
3. 합성 staging 환경에서 스키마 확장 이관과 API 호환성을 확인한다.
4. 운영 백업과 rollback 경로를 준비하고 migration을 한 번만 실행한다.
5. 호환되는 API/web을 배포하고 내부 smoke를 통과한 뒤 worker를 재개한다.
6. 실제 발송은 승인된 template·수신자·시간 정책을 확인한 feature flag로 점진 활성화한다.
7. 오류율, outbox 지연, unknown 발송, 대사 차이, 권한 거부 급증을 관찰한다.

## 백업·복구

초기 목표 제안: RPO 24시간, RTO 4시간. 실제 운영 기대와 비용에 따라 채택해야 한다. DB와 증빙 원본·메타데이터·정책 버전·암호키 복구 경로를 함께 설계한다. 암호키를 백업 데이터와 같은 공개 위치에 두지 않는다.

매월 격리 복원 연습 제안: DB 복원→증빙 객체/해시 대조→원장 합계/권한 확인→철회/tombstone 재적용→outbox 중복 발송 방지 확인. 운영 복원 도중 외부 발송 flag는 false다. 복구된 오래된 총무 역할을 검증 없이 활성화하지 않는다.

rollback은 앱 버전 복귀와 데이터 복구를 구분한다. 이미 발생한 외부 발송을 취소했다고 주장하지 않는다. 파괴적 DB downgrade 대신 호환 schema 유지 또는 승인된 백업 복원을 검토한다.

## 모니터링

관측 항목: HTTP 오류/지연, DB 연결/잠금, import 실패·중복 후보, 증빙 scan 대기, outbox oldest age, 발송 accepted/delivered/unknown/failed, 총무 공석/미연결, 미대사 거래 수, AI ACL 거부·인용 검증 실패, 백업/복원 결과. 알림 수신자는 운영 책임자로 별도 확정한다. 이 문서는 실제 모니터나 반복 알림을 생성하지 않는다.

로그는 request_id/event_id/job_id로 연결하고 원본 계좌/연락처/증빙/토큰을 제외한다. 장애 시 사용자는 마지막 데이터 시점과 처리 불확실성을 보며 중복 제출을 피할 수 있어야 한다.
