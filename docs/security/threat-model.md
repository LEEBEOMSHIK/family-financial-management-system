# 위협 모델과 데이터 수명주기

상태: 기술 통제 제안. 보관기간·위탁·동의·미성년자·법적 의무는 원문/운영 주체 검토 후 확정한다. 이 문서는 법률 적합성 인증이 아니다.

## 신뢰 경계와 통제

| 경계/위협 | 통제 | 검증 |
| --- | --- | --- |
| 외부 사용자→세션: 계정 탈취/CSRF | 초대 가입, 제공자 검증, HttpOnly/Secure/SameSite, CSRF/Origin, rate limit, 중요 작업 재인증 | 만료/회전/로그아웃/복구/CSRF 거부 |
| 구성원→다른 가족: IDOR | 매 요청 membership+role+object 검증, 가족 복합 FK | 다른 가족 ID·파일·export·검색 접근 거부 |
| 전임 총무→현재 권한 | 시점별 역할, 서버 캐시 무효화, 재인증 | 임기 종료 정각의 읽기/쓰기/발송 거부 |
| 업로드→파서/미리보기 | 형식 allowlist, 크기·압축한도, 격리, 악성코드 검사, 외부 참조/실행 차단 | 위장 확장자·zip bomb·악성 PDF·수식 처리 |
| 프론트→민감 응답 | no-store, 출력 인코딩, CSP, 개인정보 마스킹 | 브라우저 뒤로가기/공유 캐시/스크립트 주입 |
| worker→알림 공급자 | 최소 메시지, 키 보관, idempotency, webhook 서명/replay 검사 | 재시도·unknown·수신자 변경·가짜 callback |
| DB/스토리지→운영자 | 역할 분리, 저장/전송 암호화, 키 분리, 백업 접근 감사 | 비공개 객체/키 회전/복원 |
| 문서→LLM: 지시문 주입 | 자료를 데이터로 취급, ACL 선필터, 도구 최소화, 인용 검증 | 악성 문서·가족 경계·권한 철회 |
| 앱/DB 관리자→이력 변조 | append-only 앱 권한, 별도 감사 저장/백업, 선택적 hash-chain 외부 체크포인트 | 업데이트/삭제 거부·체크포인트 대조 |

모든 요청의 서버 권한 검증과 기본 거부는 [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)을 참고한다. 파일의 확장자·Content-Type만 신뢰하지 않고 저장 위치·권한·내용 검사를 함께 적용한다. ([OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html))

## 증빙 처리

영수증/PDF/이미지는 원본 객체를 비공개로 보존하고 sha256, 업로더, 업로드 시각, MIME, 크기, 연결 객체, scan 상태를 저장한다. 원본은 수정하지 않고 마스킹/미리보기/OCR은 파생본으로 관리한다. 문서 제목에도 개인정보가 있을 수 있으므로 접근 범위와 로그를 제한한다.

허용 형식 제안: JPEG/PNG/PDF, 최대 20 MiB. 스캔 완료 전 다운로드/미리보기/AI 색인을 차단한다. SVG/HTML/실행파일은 기본 거부한다. 원본은 attachment disposition으로 제공하고 미리보기는 별도 격리 경로에서 안전한 파생본을 사용한다. 짧은 수명 signed URL을 쓰더라도 발급 전 인가하며 즉시 철회 요구가 있으면 인증 프록시 스트림을 선택한다. 이미 다운로드한 파일을 원격 회수할 수 있다고 약속하지 않는다.

## 감사 이력

역할/정책/승인/원장/증빙/투표 관리/가져오기/내보내기/알림 변경을 기록한다. actor, effective role, family, action, object, before/after의 최소 마스킹 diff, timestamp, request_id, policy_version을 사용한다. 감사 이벤트 작성 실패 시 중요한 업무 트랜잭션도 실패하게 한다. 읽기/다운로드 접근 기록은 데이터 변경 감사와 별도 수명 정책으로 관리한다.

append-only와 hash-chain은 변조를 어렵게 하거나 탐지하는 통제다. DB 최고 관리자의 공격까지 막는 절대 불변성을 의미하지 않는다. 증거 강도가 필요하면 외부 체크포인트/WORM 저장과 복구 권한 분리를 검토한다.

## 데이터 분류와 보관

| 분류 | 예 | 기본 취급 |
| --- | --- | --- |
| 공개 가능 | 제품 도움말·합성 디자인 예제 | 저장소 포함 가능 |
| 가족 내부 | 승인된 공통 원장 요약·일정 | 활성 가족 구성원 범위 |
| 제한 | 개인 회비·증빙 원본·상세 수취 정보 | 업무/소유권/감사 scope |
| 비밀 | 세션·은행 token·서명키·암호키 | 비밀 저장소, 로그/Git/AI 금지 |

업무 이력 보존과 개인정보 삭제 요청이 충돌하면 정책/법적 근거를 확인하여 원장 사실 보존, 식별정보 분리·가명화, 제한 열람, 파생본/색인 삭제를 설계한다. 보관기간이 없다고 영구보관 승인으로 해석하지 않는다. 반대로 임의 날짜를 정해 자동 삭제하지 않는다. 실제 데이터 도입 전 각 분류의 기간·근거·삭제·백업 소거·법적 보존 중지(legal hold) 여부를 결정한다.

## 사고 대응

1. 영향을 받는 조회/변경/외부 발송 feature flag를 중지하고 증거·시각·범위를 보존한다.
2. 세션/키 철회, 큐 정지, 영향 가족/기간/파일을 파악한다. 로그에 민감자료를 새로 복제하지 않는다.
3. 책임자가 통지/복구 범위를 결정한다. 데이터 정정은 원장 정정 절차를 사용한다.
4. 격리 환경에서 복원·대사 검증 후 재개하고 원인/재발 방지 테스트를 남긴다.
